# Partial-mesh membership for Elixir at scale

> *Why your libcluster setup cracks at ~80 nodes, and what to do about it.*

If you've ever tried to scale an Elixir cluster past 50–100 nodes, you've
probably watched it stall in interesting ways. `:net_kernel` gets chatty.
Heartbeats start arriving late. A noisy network blip turns into a
partial-partition cascade that needs an operator to untangle. Phoenix
PubSub fanout balloons. Eventually you stop adding nodes, even though
your workload says you should.

This post is about why that happens, why the well-known fix (HyParView, the
membership protocol that Riak Core and Partisan are built on) hadn't
shown up cleanly in the Elixir ecosystem yet, and what shipping it as a
focused hex package looks like.

## Full mesh is fine, until it isn't

Erlang distribution is a beautiful hammer. `Node.connect/1`, `:rpc.call/4`,
`Node.send/2` — and your single-node-feels code runs across machines.
This works because every connected pair of nodes maintains a TCP
connection and keeps it warm with `:net_kernel` heartbeats.

That's a *full-mesh* topology: an N-node cluster has N(N-1)/2 connections.
For ten nodes, 45 connections. For a hundred, 4,950. For a thousand,
half a million.

Empirically, you start hitting walls around 80–120 nodes:

- `:net_ticktime` heartbeats don't scale linearly. Past a certain point,
  late heartbeats cause spurious node-down detections.
- A short network blip looks like one failure to a small mesh and
  N-1 simultaneous failures to a large mesh, which is much harder to
  recover from cleanly.
- Phoenix.PubSub broadcasts are O(N) per node per message. At 100 nodes
  with 10 broadcasts/sec, every node is doing 1,000 sends/sec just for
  pubsub.

The fix isn't to make Erlang distribution faster (it's already great).
It's to use Erlang distribution for a *bounded* set of peers and
something else — gossip, in this case — for the rest of the system's
shape.

## libcluster's place in this

[`libcluster`](https://hex.pm/packages/libcluster) is the standard way
Elixir apps discover their fellow nodes. It supplies *strategies* —
Gossip (UDP multicast), EPMD, Kubernetes, DNS, ECS — that all answer
the same question: "what nodes should I be in a cluster with?" Then
they call `Node.connect/1` for each of them.

This is fine for small-to-medium clusters and handles the discovery
problem nicely. But every libcluster strategy assumes the answer is
"all of them" and produces a full mesh. If you have 200 pods in your
Kubernetes deployment and they all run libcluster_kubernetes, you have
200 nodes, ~20,000 distribution links, and the problems above.

## HyParView in 90 seconds

[HyParView](https://www.dpss.inesc-id.pt/~ler/reports/dsn07-leitao.pdf)
is a 2007 paper by João Leitão, José Pereira, and Luís Rodrigues. It
proposes a *hybrid partial-view* membership protocol. The protocol is
the substrate underneath Riak Core, Plumtree, and Partisan — none of
which previously had a clean Elixir-native standalone implementation.

Each node maintains **two views**:

- **Active view** — small (target `log(N) + 1`, defaults to 5 peers
  for ~30 nodes). Symmetric, TCP-connected. This is your messaging
  substrate.
- **Passive view** — larger (`K · (log(N) + 1)`, default `K=6` so
  roughly 30 entries). Held in reserve. Refreshed lazily through
  periodic gossip (the *shuffle*).

Three things happen with these views:

1. **Joining**: a new node sends a `JOIN` to a contact. The contact
   adds the joiner to its active view, then sends `FORWARD_JOIN`
   along an active-view random walk so the joiner gets seeded into
   peers further away.
2. **Repairing**: when an active-view peer fails (TCP close, blocking),
   the survivor picks a random peer from its passive view and sends
   `NEIGHBOR` to promote it into the active view.
3. **Shuffling**: every ~30s, each node samples its active and passive
   views and forwards the sample to a random active-view peer along
   another random walk. The receiver merges the sample into its own
   passive view. This keeps passive views fresh and ensures eventual
   convergence.

The result, demonstrated in the paper: under massive node failure (up
to 95% of nodes failed simultaneously), HyParView recovers reliable
broadcast in **fewer than 4 membership rounds**, vs. tens of rounds
for naive cyclic protocols. And it does it with a fanout near `log(N)`,
so each node is doing ~5 sends per broadcast, not ~100.

## Why two views

The "hybrid" name comes from combining two membership-maintenance
strategies:

- A **reactive** strategy on the active view — TCP gives you fast,
  cheap failure detection (closed socket = peer gone). The downside
  is reactive strategies don't repair themselves under heavy churn.
- A **cyclic** strategy on the passive view — periodic gossip
  ensures the passive view stays diverse and low-clustering, so when
  the reactive layer needs a replacement, there's one available with
  good graph properties.

You couldn't get away with just one view. Pure reactive (Scamp) leaves
you with skewed in-degrees and brittle behaviour under heavy failure.
Pure cyclic (Cyclon) takes too many rounds to react to failures. The
hybrid works because the views serve different purposes and are
maintained on different time scales.

## The shape of the library

I [shipped this as a hex package](https://hex.pm/packages/hyparview) in
v0.1. The library is intentionally narrow — it implements *exactly*
HyParView, nothing more. Broadcast (Plumtree), distributed registry
(Horde), TLS, RPC — all out of scope. Membership is its own concern.

The architecture has three layers:

```
                 ┌─────────────────────────────┐
                 │  HyParView.State (pure)      │
                 │  views, transitions, actions │
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────┴──────────────┐
                 │  HyParView.Server (GenServer)│
                 │  timers, transport, telemetry│
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────┴──────────────┐
                 │  HyParView.Transport         │
                 │  (behaviour)                 │
                 └────┬───────────────┬─────────┘
                      │               │
            ┌─────────┴───┐  ┌────────┴─────────┐
            │ Transport.  │  │ Transport.TCP    │
            │ Test        │  │ + Connection      │
            │ (in-proc)   │  │ (gen_statem)      │
            └─────────────┘  └───────────────────┘
```

The pure `State` core was the most important architectural choice. All
seven invariants from the paper — view-size bounds, no overlap, eventual
symmetry, eviction-demotes-to-passive, deterministic-RNG — are
verified as `StreamData` properties against this layer alone, no
GenServer, no transport, no time. That's how you keep a protocol
implementation honest: separate the algorithm from the runtime.

The Server is a thin shell on top: timers for the shuffle tick, a
subscription mechanism for `:peer_up`/`:peer_down` events, telemetry
events, a `connection_lost/2` API for failure reporting. Most users
never touch the State layer directly.

The Transport behaviour is what makes this library actually useful in
practice. It's pluggable. The library ships two implementations: an
in-process Test transport (Registry-based, used by the test suite and
useful for application tests) and a real TCP transport built on
`:gen_tcp` and per-peer `:gen_statem` connection processes. The TCP
transport handshakes peer identities on connect (so each side knows
who it's talking to), uses `packet: 4` framing for message boundaries,
and signals `:peer_lost` when a connection breaks — which the Server
translates into `State.connection_lost/2`, kicking off reactive repair
automatically. No application code needed for TCP failure handling.

## Where libcluster fits

Now the structurally-interesting question: how does this slot into a
real Elixir app?

The honest answer is *adjacent*, not "replaces libcluster." HyParView
gives you partial-mesh *logical* membership. Erlang distribution wants
to give you full-mesh *physical* connections. They're solving
overlapping but distinct problems.

There's a clean integration path: **boot the BEAM with `-connect_all
false`, run HyParView for membership, and call `Node.connect/1` only
for peers in HyParView's active view.** That gives you partial-mesh
BEAM distribution — a thing the Elixir ecosystem doesn't have a
production-ready story for today.

I packaged this as a companion strategy:
[`libcluster_hyparview`](https://github.com/b-erdem/libcluster_hyparview).
It's a `Cluster.Strategy.HyParView` module that:

1. Starts a `HyParView.Server` per node with the topology config.
2. Subscribes to its events.
3. On `:peer_up`, calls `Cluster.Strategy.connect_nodes/4`.
4. On `:peer_down`, calls `Cluster.Strategy.disconnect_nodes/4`.

```elixir
config :libcluster,
  topologies: [
    hp_example: [
      strategy: Cluster.Strategy.HyParView,
      config: [
        local_peer: HyParView.Peer.new(node(), {{0, 0, 0, 0}, 4500}),
        contacts: [
          HyParView.Peer.new(:"app@10.0.0.1", {{10, 0, 0, 1}, 4500})
        ]
      ]
    ]
  ]
```

With `-connect_all false` and this strategy, every node in your fleet
keeps Erlang distribution links to a small bounded set of peers, with
the rest of the cluster reachable through HyParView's gossip overlay
for protocols that need it.

## What's next

`hyparview` v0.1 is a building block. The natural things to build on
top:

- **Plumtree.** HyParView's overlay is unbiased random; Plumtree
  builds an epidemic broadcast tree from it. Pair them and you have
  reliable broadcast that scales linearly with cluster size, not
  quadratically.
- **Partial-mesh Phoenix.PubSub.** PubSub today is full-mesh `:pg`-
  based. A version that broadcasts only to active-view peers (with
  Plumtree fanout) would cut tail latency on busy systems substantially.
- **Substrate for distributed registries.** Horde's CRDT-based
  registry assumes full mesh. There's no fundamental reason it has
  to.

Most of the interesting distributed-systems work in the Elixir ecosystem
has been done assuming full mesh. With a clean partial-view membership
primitive, a lot of that becomes worth re-examining at the scale where
it actually matters.
